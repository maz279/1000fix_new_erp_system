## 1. Purpose

`PGD-AUDIT-001` `PGD-A1-05` recorded *"designing ~660–1,500 screens — not estimated, in no plan"*
and labelled the figure *"an order-of-magnitude inference from 12 portal specifications and 14 admin
workspace copy packs, **not a count**."* `GV-007` §6.1 carried it forward as **estimate class 5**,
which under rule `EM-05` capped the whole screen-design estimate at class 5 — a band of
**95–325 PW**, expected 180 PW, on a driver nobody had counted.

`GV-007` then instructed: *"`UX-003` must convert this to a count before `GV-008` is baselined."*

**This document is that count.** It enumerates the screen estate from counted drivers, classifies
every screen by the design effort it actually requires, and restates the effort on that basis. The
headline result is not the one the register expected:

> **1,404 screens — near the top of the inferred range — but only 466 of them require a design
> artefact, and only 130 require an original one.** The other 782 are generated by the Odoo view
> conventions `AR-007` already specifies, and 156 are utility screens designed once and reused
> across thirteen surfaces.
>
> **The screen count went up. The effort estimate went down, and its band narrowed from 230 PW
> wide to 58 PW wide: 88–146 PW, expected ~109 PW.**

It unblocks the design programme itself (`UX-004` knows which flows to prototype), the front-end
build sequence (`BE-004`), the `GV-008` budget baseline, and the training and help estates, which
cannot describe screens that have not been enumerated.

# 3. What Counts as a Screen

An inventory is worthless if two people counting it get different numbers. This section is the
counting rule.

## 3.1 The definition

> **`SIR-01`.** A **screen** is an addressable primary-content state with its own route (`UX-002`
> §7.1), its own heading, and its own set of the six data states in §6.1.

| Is a screen | Is **not** a screen |
|---|---|
| A list of service orders | A filter applied to that list *(a view state — `UX-002` `NVR-40`)* |
| A service order detail | A tab within that detail *(a sub-route; counted as 0.5 — `SIR-03`)* |
| A booking step | A validation error on that step *(a state — §6.1)* |
| A confirmation dialog that blocks the flow | A toast *(feedback, not content)* |
| A full-page wizard step | An inline disclosure |
| An empty state with its own route | The empty state *of* a list *(a state of that screen)* |

| # | Rule |
|---|---|
| `SIR-02` | A modal that **collects input and can be linked to** is a screen. A modal that **confirms** is not — it is a state of the screen beneath it |
| `SIR-03` | A record tab counts as **0.5** of a screen: it needs a layout but not a full frame, heading, empty state and error state of its own |
| `SIR-04` | **A report is not a screen.** The 920 report definitions in `D-9` are rendered by ≤ 6 report-viewing screens plus the `P06` boards — see §5.5 |
| `SIR-05` | The same screen rendered in another locale, theme or density is **the same screen**. It is not counted twice, and it is designed once with §6.2 obligations |
| `SIR-06` | A screen that exists on both `P01` web and `P01` app is **two screens** where the layout genuinely differs, one where it does not. §5.2 counts the app at 2.5× its capability areas rather than 4×, which is this rule expressed as a factor |

## 3.2 Why the definition matters to the number

Under a looser definition — counting filters, tabs and confirmations — the same estate yields
roughly **3,000**. Under a tighter one — counting only unique layouts — roughly **500**. Neither
number is wrong; both are useless without the rule that produced them. **The 1,404 in §5 is the
`SIR-01` count and only means anything alongside `SIR-01`…`SIR-06`.**

# 4. Screen Classification

## 4.1 The four classes

**This is the finding that changes the estimate.** `GV-007` §6.2 splits screens 35% unique / 65%
variant. That split is reasonable for a hand-built portal estate. It is wrong for this estate,
because **`P03` is an Odoo back office and most of its views are generated from the model by the
conventions `AR-007` already specifies.**

| Class | Name | Definition | Design artefact required | Effort |
|:--:|---|---|---|---|
| **G** | **Generated** | A standard Odoo list, form or search view produced from the model per `AR-007` view conventions, or a dashboard configured in Metabase/Grafana | **None.** Conformance review only | ~0.05 PD |
| **P** | **Patterned** | Realised by applying an existing design-system pattern with no novel interaction | Pattern application + review | 0.2–0.4 PD |
| **B** | **Bespoke** | Novel interaction, dense multi-source composition, or a safety/money/custody consequence | Full wireframe, all states, field-level specification, review | 1.0–1.5 PD |
| **U** | **Utility** | Sign-in, OTP, profile, settings, notifications, consent, help, search results, 404, 500, offline, maintenance | Designed once as an archetype, applied per surface | 0.8–1.2 PD per archetype |

| # | Rule |
|---|---|
| `SIR-07` | **Class G is not "free".** It costs a conformance review against the `P03` workspace pattern library, and it costs the pattern library itself — a one-off in §11 |
| `SIR-08` | A screen is **Class B** if any of: it composes data from ≥ 3 modules; it carries a money, custody or safety consequence; it is one of the 15 critical journeys' decision points; it must work offline; or it has no precedent in the pattern library |
| `SIR-09` | **Class is assigned once, at inventory, and may only be raised.** A screen may move P → B when design reveals novelty. It may not move B → P to save budget without a Design Authority decision |
| `SIR-10` | Class G requires that `AR-007`'s view conventions actually exist and are enforced. **If they are not, 782 screens silently become Class P and the estimate is wrong by ~130 PD.** This is the single largest dependency in §11 |

## 4.2 Why `P03` is overwhelmingly Class G

`P03` surfaces 67 modules and 371 functional areas through the Odoo web client. In Odoo, a list
view and a form view are declarative XML derived from the model definition; `AR-007` specifies the
conventions. A designer does not draw them — a designer draws the **pattern** once, and the
convention reproduces it 742 times.

> **The design work in `P03` is not 742 screens. It is fourteen workspace landing screens, one
> pattern library, and thirty wizards.** That is the insight the class-5 estimate could not contain,
> and it is worth roughly **60 PW**.

## 4.3 Where the class split is a risk, not a saving

| Risk | Consequence |
|---|---|
| `AR-007` conventions are thin or unenforced | 782 Class G screens become Class P; +~130 PD |
| A generated view is inadequate for a high-frequency task | It is reclassified B; each reclassification is +1.0–1.5 PD |
| Bengali breaks a generated view's density (`LAY-03`) | Systematic, not per-screen — fixed in the pattern library, but must be found early |
| `P05` uses Odoo Portal templates that are less conventional than back-office views | 20 Class G screens at risk; `P05` is W3 so the risk is discoverable in W1 |

## 4.4 `GV-006` `Q-03` — are screens scope products?

> **Ruling.** **Screens are attributes of the twelve portals, not products in their own right.**
> Baseline `SB-3` already carries the twelve portals; adding 1,404 screens as scope items would
> triple the baseline's row count without adding a decision anyone can take.
>
> **But the design effort is a separate work stream** (`GV-007` stream 4) and must appear in the
> plan, the budget and the resource ramp. The class split in §5 is the unit that stream is
> estimated and tracked in — not the screen count.

## 4.5 `AR-003` `Q-04` — do portals need SDDs?

> **Ruling.** Class **B** screens need an SDD entry, because they carry behaviour an SDD describes.
> Class **P**, **G** and **U** screens do not — they are covered by the component contract
> (`UX-001` §8) and the view conventions (`AR-007`). **130 SDD entries, not 1,404.**

## 6.4 `UXA-07` — the copy estate is not what the register claims

The register's Category 06 preamble states the programme *"has written 42 UI copy packs — every
label, every error message, every empty state, in two languages."* Counted at 2026-08-18 14:45 (+06):

| Measure | Count |
|---|---:|
| Copy packs | 42 |
| **Screen-copy sections across all 42 packs** | **114** |
| Sections in the twelve portal packs | 43 |
| Sections across the fourteen workspace packs | 18 |
| **Distinct i18n keys written** | **696** |
| Screens in this inventory | **1,404** |

**696 keys and 114 screen sections against 1,404 screens is exemplar coverage, not complete
coverage.** A twelve-surface bilingual ERP needs strings in the tens of thousands. The packs are
excellent — they establish the pattern, the terminology bindings, the character budgets and the
Bengali forms — and they are **approximately 8% of the string estate by screen section**.

> **This does not diminish the packs; it corrects the register.** The consequence is real: `GV-007`
> stream 2 sized content at 520–775 PW against 477 files, and the remaining UI string work is
> inside that band only if it was counted. It was not. **Raised as `UXA-07` to `GV-007` and
> `CG-014`.**

**= 88 – 146 PW.** Three-point expected value at M = 528 PD: **E = 547 PD ≈ 109 PW.**

## 11.2 Against the class-5 estimate

| | `GV-007` §6.3 (class 5) | **This document (class 3)** | Change |
|---|---|---|---|
| Driver | 660–1,500 screens, inferred | **1,404 screens, counted** | Within range, near the top |
| Effort band | 95 – 325 PW | **88 – 146 PW** | Band narrows from 230 PW wide to **58 PW** |
| Expected | ~180 PW | **~109 PW** | **−39%** |
| Estimate class | **5** (driver), capped by `EM-05` | **3** (driver counted; rate model unchanged at class 3) | **Class 5 → 3** |

> **Why a higher screen count produces a lower effort.** `GV-007` §6.2 applied a 35/65 unique/variant
> split to the whole population. This estate is not 35/65 — it is **9% bespoke, 24% patterned, 56%
> generated, 11% utility**, because `P03` is an Odoo back office whose views are produced by the
> conventions `AR-007` specifies. The class-5 model could not see that, because a model applied to
> an uncounted driver cannot be applied to its structure either.

## 11.3 What would invalidate this

Stated, because an estimate whose failure modes are not written down will be quoted as certain.

| # | Condition | Effect |
|---|---|---|
| 1 | **`AR-007` view conventions are thin or unenforced** (`SIR-10`) | 782 G → P; **+130 PD** |
| 2 | Bengali density (`LAY-03`) forces a bespoke table pattern per workspace | +14 × 1.5 = **+21 PD**, plus rework |
| 3 | The workspace allocation (§5.3) is rejected and workspaces are re-cut | Re-derivation, **+15–25 PD** |
| 4 | `UI` copy coverage gap `UXA-07` is charged to design rather than content | Out of scope here; **+ up to 200 PD** to content |
| 5 | Class B reclassification runs above 15% (`SIR-09`) | **+20–30 PD** per 20 screens |
| 6 | `P06` dashboards are rebuilt natively rather than configured | +24 screens at Class B; **+30 PD** |

## 11.4 The recommendation

> **`GV-007` §6.3 and `GV-008` should adopt 88–146 PW, expected 109 PW, at estimate class 3**,
> and carry conditions 1 and 4 of §11.3 as named risks in `GV-005`. This is offered, not applied:
> re-baselining an estimate is `GV-006`'s procedure and the Change Board's decision.
