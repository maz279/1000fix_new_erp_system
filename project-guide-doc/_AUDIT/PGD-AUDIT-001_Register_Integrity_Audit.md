## 1. Purpose and Method

This audit is **mandatory under the commissioning instruction** and was performed on the register
immediately after issue, before any consumer relied on it.

It applies the same three methods the repository's own audits use (`00-06` §1), plus one added
because this register makes claims about files rather than about business logic:

| # | Method | What was checked |
|---|---|---|
| 1 | **Structural consistency** | Row counts per category, ID uniqueness, ID-set agreement between the register and all 17 category overviews, link integrity, code-space collisions |
| 2 | **Arithmetic consistency** | The §0.5 summary table against the seventeen category tables; the §2.1 blocking count against the ⛔ population; the grand total against the row count |
| 3 | **External verification** | Every file-count, keyword-count and file-absence claim re-executed against the filesystem |
| 4 | **Temporal verification** *(added)* | Whether the estate changed between first enumeration and issue — the failure mode `AUDIT-016` `AP-17` raised and proposed rule `RG-08` for |

**Result: 2 critical, 4 high, 5 medium and 2 low findings — 13 in total.**
**Eleven are closed. Two remain open** — both requiring a decision this repository cannot make.

Every closed finding is recorded rather than silently corrected, because a register whose own
error history is hidden cannot ask the rest of the programme to disclose theirs.

> **Revision 1.1 — 2026-08-18.** The v1.0 issue of this audit stated *"13 findings, 2 critical,
> 4 high"* and *"seven closed, six open"*. Counting the finding sections returns **12**, of which
> **3** are High, and the closed/open split was **6/6**. **This audit committed the same arithmetic
> error it raised as `PGD-A1-02`.** It is recorded as `PGD-A1-13` rather than silently corrected.
>
> Two further findings — `PGD-A1-08` and `PGD-A1-11` — were closed by remediation after v1.0, and
> `PGD-A1-12` is reclassified *Closed — accepted*. The table below is the corrected position.

# 3. Critical Findings

## PGD-A1-01 — Identifier collision with `project_content` category 99

**Severity: Critical · Type: Identifier-space violation · Status: CLOSED at issue**

The register's category 99 was originally allocated the code **`RF`**. During the temporal
verification pass it emerged that `project_content` category 99 **already uses `RF`**, and that two
files had been authored into it during this register's own drafting:

| File | Written | Size |
|---|---|---:|
| `project_content/99_Reference_and_Registers/RF-001_ERP_Glossary_and_Acronym_Register.md` | 2026-08-18 01:27 | 38 KB |
| `project_content/99_Reference_and_Registers/RF-002_Source_Document_and_Evidence_Index.md` | 2026-08-18 01:30 | 26 KB |

`RF-001` would therefore have denoted two different documents in the same programme.

**Consequence.** This is the exact failure mode of finding **`AF-11`**, where the website and ERP
content sets used identical-looking priority letters (`P1–P4` vs `P0–P3`) with different meanings.
Left uncorrected it would have been a permanent defect, because identifiers are permanent.

**Remediation applied.** Category 99 renamed **`RF` → `RR`** across all 20 files before issue.
`RF-001` (content glossary) and `RR-001` (engineering glossary) are now distinct. A cross-reference
note is carried in both the register §CATEGORY 99 preamble and the category overview.

**Root cause.** The register allocated a new code space without first checking the three existing
code spaces in the workspace. This is precisely the gap that `RR-002` (Identifier Convention
Standard) exists to close — **the register's own authoring reproduced the defect it was written to
name.** That is recorded here rather than smoothed over.

## PGD-A1-02 — Grand total wrong; summary table disagreed with the register body

**Severity: Critical · Type: Arithmetic inconsistency · Status: CLOSED at issue**

The first issue of §0.5 stated **139 documents**. Counting the rows returns **140**.

Worse, the summary table disagreed with the seventeen category tables on **eight of seventeen
rows**, and conflated ⬜ (absent) with ⛔ (absent and blocking) into a single column, which made the
error invisible:

| Category | First issue (✅/◐/absent) | Counted | Δ |
|---|---|---|---|
| 00 Governance | 1 / 6 / 4 | 0 / 6 / 5 | ✗ |
| 01 Requirements | 0 / 6 / 4 | 0 / 5 / 5 | ✗ |
| 02 Architecture | 1 / 3 / 9 | 0 / 3 / 10 | ✗ |
| 03 Data | 0 / 4 / 5 | 0 / 6 / 3 | ✗ |
| 04 Integration | 0 / 3 / 5 | 0 / 5 / 3 | ✗ |
| 05 Security | 0 / 3 / 8 | 0 / 2 / 9 | ✗ |
| 08 Quality | 0 / 4 / 7 | 0 / 7 / 4 | ✗ |
| 12 Release | 0 / 1 / 5 | 0 / 2 / 4 | ✗ |
| 99 Reference | 0 / 1 / 5 | 0 / 2 / 4 | ✗ |

**Consequence.** The headline finding of the register — *"4 of 139 exist"* — was itself wrong. The
correct figure is **2 of 140**, which is a materially worse position than the one first published.

**Remediation applied.** The summary table was rebuilt by counting status symbols in the category
tables, ⬜ and ⛔ separated into two columns, the ⚠ column marked explicitly as a subset of ✅ and
excluded from the total, and a verification note added under the table pointing at this finding.

Post-remediation machine verification:

```
Register rows counted:  140
✅ 2   ◐ 60   ⬜ 21   ⛔ 57      (2 + 60 + 21 + 57 = 140 ✓)
Duplicate IDs:          none
Overview ↔ register ID-set agreement:  17 of 17 categories ✓
Overview ↔ register status agreement:  140 of 140 rows ✓
```

**Root cause.** The summary table was written from intent before the category tables were finished,
then never recounted — a direct breach of inherited rule **`RG-06` — count, do not consult**, which
the register itself cites in its own control section.

## PGD-A1-03 — The enumeration baseline moved during authoring

**Severity: High · Type: Temporal integrity · Status: CLOSED at issue**

The workspace was enumerated at **01:16** and again at **01:39**. It changed in between:

| Location | At 01:16 | At 01:39 |
|---|---|---|
| `project_content/` total files | **462** | **468** |
| `project_content/19_Multimedia_and_Asset_Specs/` | **empty** | 4 files (`MM-001`…`MM-004`, written 01:18–01:29) |
| `project_content/99_Reference_and_Registers/` | **empty** | 2 files (`RF-001`, `RF-002`, written 01:27, 01:30) |
| Workspace total (excl. this repository) | **595** | **601** |

**Consequence.** Six statements in the first issue were stale within twenty-three minutes,
including two status assignments (`RR-001` and `RR-004` were marked ⛔ against files that existed by
the time of issue) and the assertion that `project_content/99_Reference_and_Registers/` is *"an
empty folder"*.

**Remediation applied.** All counts restated to the 01:39 enumeration (`462`→`468`, `595`→`601`);
`RR-001` and `RR-004` restated **⛔ → ◐**, which reduced the ⛔ population from 59 to 57; the
category 99 overview reissued at v1.1 with a "baseline movement" section; timestamps recorded in
this audit's front matter.

**Root cause and significance.** This is `AUDIT-016` finding **`AP-17`** reproduced exactly — *"the
427 figure stamped four minutes earlier caught 17 `OP` mid-authoring at 15 of 16"* — for which rule
**`RG-08`** was proposed and never ratified. **This audit is the second independent occurrence.**
The recommendation at `R-02` below asks for ratification.

## PGD-A1-04 — §2.1 understated the blocking population by a factor of nearly three

**Severity: High · Type: Arithmetic inconsistency · Status: CLOSED at issue**

§2.1 was headed *"The 21 blocking documents"* and stated that *"of the 83 absent documents, 21 are
marked ⛔ blocking."* The actual ⛔ population at first issue was **59**; the table listed 21 rows
covering 24 identifiers.

**Consequence.** A reader planning remediation would have believed the blocking backlog was 21
documents when it was 59 — a planning error of roughly 2.8×, in the section of the register
specifically written to drive sequencing.

**Remediation applied.** The section is retitled *"The critical path — 24 of the 57 blocking
documents"* (57 after `PGD-A1-03`), the true population is stated, and the remaining 33 are
explicitly deferred to the §2.2 sequencing tranches rather than left unaccounted.

## PGD-A1-05 — The register commissions a fourth unbudgeted work stream

**Severity: High · Type: Omission · Status: OPEN**

The programme already carries two effort variances:

| Variance | Size | Finding |
|---|---|---|
| Build effort measured vs approved | 1,513 PW vs 834 PW | `AF-08`, `H-02` |
| Content production, not in the business case at all | 520–775 PW | `AF-09` |

This register adds a third and surfaces a fourth:

| Variance | Size | Status |
|---|---|---|
| **Producing the 138 unwritten guiding documents** | **not estimated** | Raised here |
| **Designing ~660–1,500 screens** (`UX-003`) | **not estimated, in no plan** | Raised here |

**Consequence.** The register tells the programme what it owes and does not tell it what that
costs. Presenting the gap without the price invites the gap to be acknowledged and not funded —
which is how the content estate reached 468 files with no budget line.

**Remediation required.** `GV-007` (Estimation Model & Resource Plan) must size both, and `CO-005`
(TCO Model) must absorb both, before `GV-008` (Budget Baseline) is presented. Tracked as
recommendation **R-04**.

**Note on the screen estimate.** The `UX-003` figure of ~660–1,500 screens is an *order-of-magnitude
inference* from 12 portal specifications and 14 admin workspace copy packs, not a count. It is
labelled as such in the register. It is stated because an unstated estimate of that size is a worse
error than an imprecise one.

## PGD-A1-08 — The ◐ status had no evidence standard

**Severity: Medium · Type: Unfalsifiable classification · Status: CLOSED 2026-08-18**

**Sixty of 140 documents — 43% — carry ◐ "partially covered".** The register defines ◐ as *"material
exists but is scattered, or covers only part of the scope"*, which is a judgement, not a test.

**Consequence.** ◐ is the status most likely to be read as "nearly done" by a reader in a hurry, and
it is the status covering the largest population. Without a coverage test, a category can move from
◐ to ✅ by assertion.

**Remediation applied.** `PGD-000` §0.3 is reissued as **"Status legend and evidence standard"**
with a fourth column stating the test for each status. ✅ now requires all four of: a named file at
a stated path; complete front matter; **≥90% of the section set its governing standard requires,
counted section by section**; and a named owner with an approval record. ◐ requires a named file
and section cited in the register row, and is explicitly defined as *"absent, with useful source
material — not nearly done"*. ⛔ now requires the blocking dependency to be **named in the row**.

**Residual.** The ✅ test (c) measures against per-document-type section sets that `RR-003` has not
yet published. Until it does, **no ◐ may be promoted to ✅** — stated in the legend. `RR-003`
remains recommendation **R-03**.

## PGD-A1-09 — The register cannot be baselined by any existing body

**Severity: Medium · Type: Governance circularity · Status: OPEN**

`PGD-000` §3 states that changes require *"a Change Request approved by the ERP Steering
Committee"*. `GV-002` records that the Steering Committee's terms of reference **do not exist**, and
`GV-001` records that the Programme Charter is unapproved.

**Consequence.** The register nominates an approver that has no constituted authority. This is not
unique to the register — it is true of all 601 files, every one of which is marked `DRAFT FOR
APPROVAL` — but it means `PGD-000` cannot become binding by its own mechanism.

**Remediation required.** `GV-001` and `GV-002` are the only documents in the register that can be
approved without a prior approval, and they must be first. This is already reflected in the §2.2
sequencing (tranche **T0 — Authority, weeks 0–2**).

## PGD-A1-12 — Markdown lint warnings across all files

**Severity: Low · Type: Cosmetic · Status: CLOSED — accepted**

The editor reports `MD022` (blanks around headings), `MD025` (multiple H1) and `MD036` (emphasis as

## PGD-A1-13 — This audit's own findings arithmetic was wrong

**Severity: High · Type: Arithmetic inconsistency · Status: CLOSED at revision 1.1**

The v1.0 issue of this audit stated, in three separate places, that it contained **13 findings —
2 critical, 4 high, 5 medium, 2 low — of which seven were closed and six open.**

Counting the finding sections returns:

| Claimed in v1.0 | Counted | |
|---|---|:--:|
| 13 findings | **12** | ✗ |
| 4 High | **3** | ✗ |
| 7 closed / 6 open | **6 closed / 6 open** | ✗ |

It also asserted under `PGD-A1-11` that *"link verification is now part of the issue checklist"*
when no checklist existed in any file.

**Consequence.** The audit that raised `PGD-A1-02` — *"the summary table was written from intent
before the underlying rows were finished, then never recounted"* — **committed exactly that error
about itself, in the same session, having just named it.** Any reader taking the audit's finding
count at face value would have been given a wrong number by the document whose purpose was to
supply correct ones.

**Remediation applied.** The summary is regenerated by counting finding sections and severity
lines; a per-finding status table is added so the roll-up can be checked against rows without
reading the body; rule **`PG-M10`** now requires every roll-up to be regenerated from its source
rows immediately before issue; the unsupported checklist claim is discharged by actually publishing
the checklist. With this finding added the totals reconcile: **13 findings — 2 critical, 4 high,
5 medium, 2 low; 11 closed, 2 open.**

**Root cause and significance.** Three findings in this audit — `PGD-A1-02`, `PGD-A1-07` and this
one — are the same defect: **a summary written before the thing it summarises was finished.** That
it recurred *within the remediation of its own first instance* is the strongest available argument
that the control must be mechanical (`PG-M10`) rather than a matter of care. It is also the
strongest available argument for recommendation **R-07**, independent assurance: a function
checking its own arithmetic missed it twice.
