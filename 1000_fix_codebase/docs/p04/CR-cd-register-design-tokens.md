## Situation

`P04-M07` builds the design-system foundation: one DTCG token source
(`libs/ts/ui/src/tokens/tokens.json`), one component contract
(`docs/design-system/component-contract.md`), realisations for every runtime
(DSY-01). The R1 realisation must ship inside an Odoo module so the Odoo
asset bundler compiles it (`P04-M06-T04`).

BE-005 §6 (the issued module register, 331 rows, regenerated by
`tooling/cd-register/generate-cd-register.ps1` under rule CDR-11) contains
**no design-system row**: the register was issued before UX-001's
token/realisation architecture was adopted.

## Problem

FF-16 validates CD references for **form and membership**. Inventing an id
(e.g. `CD-M30-05`) would pass the regex and fail membership — correctly. The
register is *issued*, not hand-editable; a missing row is a governance gap,
not a coding gap.

## Proposal

Add one row to BE-005 §6 (then regenerate `cd-register.yaml`):

| Field | Proposed |
|---|---|
| id | `CD-M30-05` (fills an existing placeholder) |
| name | `cd_design_tokens` |
| type | Odoo module (asset-only carrier — no models) |
| wave | W1 |
| pw | 3 |
| unit | M30 (Platform Administration — the P03 shell consumes R1) |

Alternative considered: a new unit `DSY` — rejected because the register's
unit set mirrors the module register, and the carrier is consumed by M30's
P03 shell rather than standing alone.

## Interim state (until the Board rules)

`cd_design_tokens/__manifest__.py` deliberately carries **no `x_cd_id`**.
The module is otherwise fully governed: FF-17 layer discipline (platform,
depends only on `base`+`web`), FF-23 tests present, and the CFM-01…CFM-05
conformance suite is executable from this repository.

## Impact if rejected

The module remains unregistered: FF-16 keeps ignoring it (no CD id claimed),
CODEOWNERS generation skips it, and G1 evidence carries this CR as the open
item. No functional impact — the tokens and conformance suite are
infrastructure, like `libs/` and `tooling/`.
